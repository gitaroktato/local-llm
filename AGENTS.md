## Performance Benchmarking

Usually this conversation is generated by the local llama-server, so every turn's speed is already written to the server log. No benchmark tool is needed — the Studio build doesn't even include `llama-bench`.

- Log location: `~/.unsloth/studio/logs/llama-server/*.log` — one file per server start, named with epoch and port (`llama-<epoch>-port-<port>-try0.log`). The newest file is the current server.
- What the server actually runs: `ps -eo pid,etime,args | grep llama-server`. If in doubt, trust the args in the log over what the Studio UI shows.
- Per-turn speed: look for the `print_timing` line — `eval time = X ms / N tokens (T tok/s)`. For spec decoding, the same block also has `draft acceptance` and `mean len`.
- Which spec mode actually ran: the log line `spec common_specu: adding speculative implementation '<name>'` plus its params. Effective speed depends on how many draft tokens get accepted, not on raw engine speed.
- Tying a perf change to a cause: each log starts with a build banner (build number + commit hash), and the model snapshot hash is in the load section. This tells you whether a change came from the binary, the config, or the model.
- Gotcha: Studio's spec "auto" means no spec decoding at all. If you pick a drafter that isn't available (e.g. no `dflash-*.gguf` file), it silently falls back to ngram-mod instead. Always set the spec type explicitly and check the log line before measuring.
- Checking supported flags: `~/.unsloth/llama.cpp/llama-server --help` (e.g. `--spec-type` lists all implementations). Saved launch commands live in `llama-cpp-configs.md`.
- `/metrics` endpoint (Prometheus format; Studio enables it with `--metrics`, port from `ps`): send `Authorization: Bearer $(cat ~/.unsloth/studio/auth/llama_api_key_*)`. Counters count up since server start, so take two scrapes and subtract. What you get beyond the logs: per-position draft acceptance (`spec_decode_num_accepted_tokens_per_pos_total{position=N}`) tells you whether a higher `--spec-draft-n-max` would pay off, and `prompt_tokens_cached_total` / `prompt_tokens_total` shows how much of the prompt was already cached.

## Privileged Commands (sudo)

The owner executes ALL `sudo` commands personally. The agent must NEVER run sudo itself (no passwordless probing either). Instead: prepare everything else locally, then hand the exact sudo commands to the owner as a copy-paste block and wait for confirmation before continuing.


## GitHub Issues

Use `gh` CLI. Check open issues before creating to avoid duplicates:
`gh issue list --state open`

- Create an issue for new work, plans, or bugs:
  `gh issue create --title "GPU power cap plan" --body "$(cat plan.md)" --label enhancement`
- Titles: short outcome phrase, no trailing period (e.g. "GPU power cap plan").
- Labels (apply when it fits; plain to-dos may stay unlabeled):
  bug → `bug`, feature → `enhancement`, docs → `documentation`, lessons/postmortems → `lessons`.
  Add later: `gh issue edit 21 --add-label lessons`
- Plan/investigation issues: Background → Findings → Decisions → Execution Steps → Deliverables → Revert.
- Bug issues: what happened, environment (OS/driver/CUDA/model), repro steps, expected vs actual.
- Read an issue: `gh issue view 21`
- Note progress in a comment: `gh issue comment 21 --body "Applied 165W cap, results pending"`
- Reference the issue in commits as `(#N)`. Do NOT use `Closes`/`Fixes` keywords — they auto-close the issue on merge.
- NEVER close an issue yourself (no `gh issue close`, no closing keywords anywhere). Work is delivered via a merge request: commit to a feature branch, then open `gh pr create --base main --title "Short outcome phrase" --body "Work for #N"` and stop. The owner reviews and merges the PR; only after that may the issue be closed, and by the owner — not you.
- Rejections: label `wontfix`, `duplicate`, or `invalid` and comment why; closing is left to the owner.
- Plan changed mid-work? Update the body: `gh issue edit 21 --body "$(cat updated-plan.md)"`
